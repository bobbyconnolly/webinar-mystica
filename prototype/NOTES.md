# Pixel pipeline prototype

Gray-box test of the rendering pipeline for Mystica: a true-3D scene (heightmap terrain, cube characters, props) rendered through a locked UO-style camera into a low-resolution target and upscaled with nearest-neighbour sampling.

Run it: open `index.html` in a browser (no build step; Three.js r128 loads from cdnjs), or serve the folder with `python -m http.server 8765` and open `http://127.0.0.1:8765/`.

Settings can be preset in the URL, e.g. `index.html?scale=2&oblique=0&night=0.6`. In the console, `MYSTICA.S` is the live settings object, `MYSTICA.P` the player, `MYSTICA.w` the world, `MYSTICA.sim(seconds)` steps the game synchronously.

## Files

- `sim.js`: the world simulation. No rendering, no DOM, no Three.js. Terrain, sculpting, angle of repose, collision, water, entities and animal AI, the ward field and guards, the prop layout. Every function takes the world object. Loads as a browser global (`SIM`) or a Node module (`require('./sim.js')`); the server will run this same file as the authority and the client uses it for prediction. World generation uses integer hashing and a seeded generator so both ends build identical worlds.
- `main.js`: the client. Input mapping (keys, UO mouse steering, click-to-walk, touch), the Three.js scene built from the sim's prop descriptions, creature visuals and pose animation, camera, the pixel pipeline, UI. Each frame: build a player intent, `SIM.applyPlayerInput`, sculpt intents through `SIM.sculptAttempt`, `SIM.simStep`, then sync meshes from the world.
- `shaders.js`: GLSL for the object pass and the post pass.

- `net.js`: the client side of the wire. Connects to the server that served the page; with no server (file://, the published artifact, a static server) the client stays in local mode.
- `../server/server.js`: the authoritative server. Runs `sim.js` as the one true world, serves these files, talks WebSockets on `/ws`.

Headless check: `node -e "const S=require('./sim.js'); const w=S.createWorld(7); for(let i=0;i<600;i++) S.simStep(w,1/60); console.log(w.ents.length)"`.

## Server and prediction

- The server steps the world at 20 Hz. Each client's queued inputs are applied in order with their own `dt` (clamped to 50 ms, within a budget of 1.25x real time so a modified client can't move faster), through the same `SIM.stepDriven` the client uses to predict.
- Snapshots go out at 10 Hz as JSON: every entity's position, vertical state, heading and animation flags, the town's ward and guard state, events, and `ack`, the last input sequence the server applied for that client.
- Terrain goes out as binary: the full player-made state (delta, loose, faced per vertex, 56 KB) on join, then at 10 Hz only the vertices that changed since that client's last patch, 8 bytes each. Slope relaxation runs only on the server.
- The client predicts its own body: it applies each frame's input locally, sends it, and keeps it until acknowledged. On each snapshot it resets its body to the server's state and replays the unacknowledged inputs. Small disagreements are eased out over a few snapshots instead of snapping. Everything else (animals, other players, the guard) is interpolated between snapshots, 100 ms behind.
- Sculpting is not predicted: the brush intent goes to the server, the guards have their say there, and the result arrives as a terrain patch. The earth moves a beat after the shovel, which suits a slow game.
- Shared sliders (ward strength, facing, angle of repose) and per-player abilities (jump height, swimming) are sent as `tune` messages. The shared ones and `reset` are the admin's: the client sends `admin` (from `?admin=<token>` in the URL) and the server compares it with `ADMIN_TOKEN` in constant time; no token configured means nobody has them. The per-player ones stay anyone's.
- Hardening (2026-10-18, before the webinar): a malformed URL such as `/%` used to throw inside the static handler and take the process down, and a socket error (an oversized frame, invalid UTF-8) did the same through the unhandled `error` event; both are caught. `maxPayload` 4 KB (the largest honest message is a 200-character note), 200 messages a second dropped and 600 closed (4008; a client sends `in` once per frame plus strokes, so ~120/s is honest), `MAX_CLIENTS` (default 200, each connection costs a 56 KB terrain shadow and a 56 KB full-terrain send) refused with 4003. Measured with fifty players: a 15 KB snapshot per client at 10 Hz, 150 KB/s per phone, 7.5 MB/s server egress; the simulation step is 0.03 ms. Bandwidth, not CPU, is the ceiling, somewhere between 50 and 150 simultaneous players; interest management and binary snapshots are the rework beyond that.
- The published artifact cannot open WebSockets (content security policy), so it is always the offline sandbox. The networked client is the one the server serves.

## Touch controls

- Shown on coarse-pointer devices, on the first touch anywhere (hybrid laptops), or with `?touch=1` for desktop testing. The side panel and key legend start collapsed on phones.
- Left 45% of the screen is the stick zone: a floating stick appears where the thumb lands, 56 px radius, 15% dead zone, run past 80% deflection. Screen-relative like WASD.
- Right-thumb buttons: Jump, Dig (toggles sculpt mode; the tool button appears and cycles raise, lower, stone, clear), Zoom (steps 2×, 3×, 4×). A finger on the right half of the world taps to walk or, in Dig mode, applies the brush.
- Pinch on the world steps the zoom; a 30% change in finger distance is one step. Two fingers never count as a tap.
- Touch devices render at 30 fps. In touch mode the stats strip, panel and legends are hidden and the controls are drawn faint.
- **Landscape view presets** (touch devices in landscape only; portrait and desktop are untouched): the 1:1 diamond spends 22 px of height per tile of depth, so a short wide frame shows little of what is ahead. A faint View button cycles candidate fixes, applied only while landscape is held: current, 2x pixels, 32 px tiles, camera lead (the frame slides up to ~20% toward the direction of travel), vertical scale 0.75, true ortho 30 degrees. Rotating to portrait restores the player's own settings.

## Identity

A player is a device token: 32 random hex characters made on first visit and kept in `localStorage` next to the name. After `hello` the client sends `auth` with token and name; the server looks the token up in the `players` table and answers `welcome` with the body's id, colour and last position (or the spawn when the saved spot is now water or inside a wall). The same token connecting twice takes over the existing body and the old socket is closed with code 4002, so a refresh never leaves a twin. Positions are saved on every flush and on leave. No sign-up, no password; losing the browser data means a new character.

## Speech and away

Speech is local: the server delivers a `say` event only to players within 12 tiles of the speaker, and tells the speaker how many heard it; zero shows "nobody hears you" under the words. Words float for 3 s plus 0.06 s per character. On the phone the Say button opens a box with a Send button that rides above the keyboard.

When a player disconnects the body stays for 60 s, seated and labelled "(away)", then is saved and removed. Reconnecting with the same token within that minute stands the same body up again.

## The arena and the fight

A flat dirt arena of radius 16 lies north-west of the house in world terms (screen-up), at (-14, -26), outside the ward: a round stone in the middle, obelisks on the rim with two gaps, six low stone walls (block bolts and bodies), ten boulders you can hop; trees and rocks are kept out of it. It is flat on purpose: bolts move like a walker in two dimensions, so cliffs would be lies. A cobble trail with arrow signs leads from the house door, and the client shows a faint arrow toward the arena whenever you are elsewhere.

One spell, mobile first: **Magic Arrow** aims where the body faces and is one tap (the big button beside Jump; key 1 on desktop in walk mode). Casting plants the feet for 0.25 s, so you stop to shoot and the bolt (13 tiles/s, 10 tiles) visibly outruns a runner while 0.75 s of flight still leaves room to dodge. Aim assist on touch clients bends it up to 15° toward the nearest target. Cooldown 0.7 s. It bursts against whatever it hits and pops at the end of its range. Spells only work inside the arena. (Wall of Stone and Blink were tried and removed: too much.)

Around the arena lie its **grounds**: a 12-tile buffer (zone radius 28) where nobody can cast or dig but bolts can still land. A bolt's full reach is range + spawn offset + knockback = 11.1 tiles, so nothing cast at the rim ever leaves the grounds. Digging there is refused by the server and the Dig button is hidden.

**The nova** lives on the same button as the arrow: tapping fires an arrow as before; holding (the `1` key, or the Arrow button under a thumb) sends `hold: true` with each input, and `applyPlayerInput` counts `novaT` up while the holder can cast; at `NOVA_CHARGE` (3.3 s) `castNova` strikes everything within `NOVA_R` (3 tiles) of the caster, players and monsters alike, for a heart with outward knockback, roots the caster 0.4 s and puts the arrow on cooldown. No aiming: you walk up to the thing. `novaT` goes to -1 after a burst and stays there until the button is let go, so a held button fires once. Letting go early loses the charge. On a client `castNova` only resets the hold; the server's `nova` event carries the burst (a ring of magic sparks), and `nova` in each entity's snapshot (the server's `novaT`) drives the gathering sparks around anyone charging and the charge ring on the button (the label reads Nova while it gathers). `reconcile` takes the server's count and re-adds the unacked inputs' hold, so the ring does not double-count. The Arrow button captures the pointer on `pointerdown` (`setPointerCapture`) and ends the hold only on `pointerup`/`pointercancel`, never `pointerleave`: on a phone a thumb drifts a few pixels off an 88px button, and `pointerleave` was cancelling the charge so the nova never fired. A matching latent bug: `net.js`'s `ws.onopen` used to call `hooks.onOpen()` with no argument, colliding with the item-`open` message handler of the same name and throwing `reading 'id'` on every (re)connect, loudest during a deploy's reconnect loop; the socket-open callback is gone, the handshake rides on the `hello` message.

Damage is real whenever a bolt lands: 3 hearts for players, 6 for the bull, everyone regenerates a heart every 10 s. Your hearts show at the top whenever you are on the grounds or hurt; a hurt player's hearts float over their head. A player knocked to zero keels over and becomes a **ghost** with no timer: the **healer**, who wanders within 4 tiles of the spawn signpost (33 tiles from the arena centre, so out of every spell's reach by construction), makes a ghost whole again when they come within 2 tiles. The top arrow points at her while you are a ghost. Rounds still restore all participants when they end. Ghosts are glimpsed, not watched: a living player sees another's ghost only while the ghost moves and the watcher stands still; ghosts see each other. A dead bull keels over, lies a moment and sinks into the dirt. **The bull** wanders the arena; whoever hurts it is charged in bursts (3 s of charge at 6 tiles/s, a shade slower than a running player, then 2 s of standing and snorting) and gored for a heart on contact every 1.5 s, until they are down, out of the arena, or 12 s have passed since it was last hurt. A hit from any distance makes the shooter the target (there used to be an 8-tile leash, which meant far shots were ignored). Running away works; standing and shooting does not. **Waves** (`TIERS` in `sim.js`: bull, wisp, wraith): 13 s after the arena's last monster dies, the next wave rises if anyone is still on the grounds (`playersInZone`), otherwise the bull comes back; after the wraith the cycle returns to the bull. The wisp comes as a pair (`WISP_COUNT` 2, since 2026-10-19: Bobby found one easier than the bull once the arrows got faster and wider; one shoots while the other holds), the second rising a little way round the ring (`MOB_SPOTS`), one `spawn` event with a `count` for the toast, and a pair fades together when nobody is about. Kin hunt together (2026-10-19, Bobby engaged one wisp and the other watched): when a floater takes a mark, by sight or by being hurt, every other floater of its kind whose leash (sight x 1.5) reaches the mark takes it too and drifts in (`callKin`; the toast says "The other wisp comes too"). A **floater** (`updateFloater`) hovers about the arena until it sees a living player within its sight with nothing in the way (`clearLine` samples barriers along the line, so cover hides you), then holds its distance, strafes across the line of fire (switching sides every 1-2 s or when it bumps into cover or the rim) and shoots whenever the line is clear; a hit from anyone makes that person its target. The **wisp** (4 hearts, sees 11 tiles, one bolt every 1.6 s with a little scatter, keeps 5 tiles off, drifts at 2 tiles/s) and the **wraith** (7 hearts, sees 13, a volley of three 12° apart every 1.8 s, 2.8 tiles/s, keeps 6). The wraith's second spell (2026-10-19, Bobby: "the last monster is too easy", "a wall of fire or something"): 4 s after it notices you and every 9 s after while you are within 9 tiles, it hangs still with the same blink as a shot and lays a 7-tile **line of fire** through where you stand, across the line between you (`castFire`): embers for 0.6 s, then 6 s of flame; a living player on it loses a heart and is shoved out the side they came from (`stepWalls`, `HIT_INVULN` keeps a crossing to one heart, the countdown's shield to none); monsters never burn, nothing is blocked, bolts fly over. So you must step off it, and then it lies between you and the wraith: round an end, or across it for a heart, and in a round everyone else's floor too. It is a `walls` entry (the old Wall spell's list, snapshot field and renderer, with `k: 'fire'` and an `age`); the client draws three rows of flames swapped on the animation clock, a low row of embers while it rises, and a lick of flame now and then (`flameRow`, `M.FIRE`). Trying a monster out: `MYSTICA.mod.spawn('wraith')` from the admin page's console pins the arena to that wave (that monster now and after every death, fade or quiet, `pinArena`/`nextTier`; `spawn()` with nothing frees it), `MOBS=wraith` does the same at start; offline `?arena=wraith` stands you in front of one with its fire due at once, and the same parameter on the admin page online sends the spawn op after the welcome (on a plain page online it does nothing: until 2026-10-19 the sandbox ran online too, since `NET.connected` is false at load, and flashed for a frame before the live world came back; the dev sandboxes now test `OFFLINE`, the same test net.js makes). A floater hangs still for 0.7 s whenever it shoots (`FLOATER_HOLD`): that is the moment to hit it. Their body radius is 0.55, so a bolt within 0.8 tiles lands, and touch aim assist leads a moving mark by its last step's velocity (`vx`, `vz`). The lock (tap a foe, else the nearest monster in range; a player counts as a foe only while you stand on the arena grounds, since 2026-10-19 a tap on a friend at the chess table locked them and the board never opened) aims the arrow only while the mark is within `AIM_DEG` (45) of the way the body faces, `inArc`; beyond that the reticle turns grey and the arrow flies straight ahead (2026-10-18, Bobby: facing should matter). The first wisp was unhittable: it strafed at 2.6 tiles/s without pause and bolts aimed at where it was. Monsters' bolts pass other monsters. A player's arrow flies at 18 tiles/s (`SHOT_SPEED`, three times a runner; 13 until 2026-10-18, Bobby: "way too hard to hit someone") and a monster's bolt at 13 (`MOB_SHOT_SPEED`), each shot carrying its own speed `v` in the snapshot; a bolt lands within 0.55 tiles of a player (`SHOT_RADIUS`, was 0.45); and `stepShots` moves every bolt in pieces of at most 0.3 tiles (`SHOT_SUBSTEP`), each piece checked against walls and bodies, because the hit was once tested only where a whole tick's step ended (0.65 tiles at 20 Hz, 1.3 when the small container's tick stretched), so grazes landed by luck and a long tick carried a bolt clean through a body. Aim assist is not the answer in PvP (Bobby); these are symmetric. Named for later: lag compensation (the server rewinding the mark to the shooter's view, the real answer to a 300 ms round trip) and an on-hit stagger. A floater alone on the grounds for 30 s fades (event `fade`) and the bull returns: you always meet the bull first. Monsters are never saved; a restart begins at the bull. Floaters are drawn hovering (`makeFloater`, bobbing body over a ground shadow) and die in a magic burst rather than blood. Damage anywhere flashes the body white for a few frames and throws red sparks; the victim's screen edge flashes too.

On the phone the Arrow button takes the bottom corner while you are in the arena and Jump, Dig and Zoom slide one column inward, so the spell is under the thumb in portrait and landscape alike.

A round starts when someone standing in the ring uses the stone (`startRound`, via the server's `use`; or `MYSTICA.mod.round()` from the admin page, for the show); nothing starts by itself (2026-10-19: two players fighting the wraith found themselves in a round and its board in the middle of the screen; from the 17th to then two players in the ring began one on their own). The stone used alone says "Nobody else is in the ring", during a round "A round is already on". The countdown (`stepRound` in `sim.js`) is 4 s when they are the only players on the grounds, 7 s when others are nearby and might run in (13 until 2026-10-18: the wait is shielded now and should be short; fewer than two cancels it), and each new arrival in the ring during the countdown puts 7 s back on the clock, never past `COUNTDOWN_MAX` (30 s) from the first call, so fifty students arriving over a minute all start together instead of the first two starting a round the rest can only fall into (`round.here`, `round.began`, server-side). Nobody standing in the ring can be hurt during the countdown (`shielded` in `sim.js`: a bolt breaks on the body with the splash burst and sound, the bull cannot gore), and at "Fight!" everyone in the arena is a **contender** with full hearts, standing where they stood. Until 2026-10-18 the start scattered everyone to spots on the rim, and a contender who stepped over the rim fell at once, which with two fighters ended the round, restored both 8 s later and, both still being in the ring, started a new countdown that scattered them again: Bobby read the pair as "the fight resets while we are engaged and teleports us". A contender who dies, or is out of the ring or disconnected for `OUT_GRACE` (3) seconds (`round.out` keeps each one's clock, server-side only), has **fallen**: a ☠ floats over them, they may come back via the healer and keep fighting, and their kills and hits count, but they cannot win; late arrivals are fallen from the start. The round ends when a single contender is left unfallen, whoever landed the blows (or with no winner if the last two fall together), then an 8 s banner with the scoreboard, then lobby with everyone restored. Bolts are server-only state carried in snapshots; the client never spawns one, but it predicts the casting root and the cooldown (`castSpell` returns early in client mode), so the body stops where the server will stop it, and it flies the bolts on between snapshots at their known speed, holding at a wall or a body, with a snapshot's correction eased out of the drawn position (`flyShots` in `main.js`). Unacknowledged inputs are replayed at the sim time each was made (which is why the root is a window, `rootFrom` to `rootUntil`: an input from before the cast must still move; the wedge detector's clock is restored after the replay, since it counted those inputs once already; rooted feet are not a wedge; and only the server moves a wedged body, a predicting client waits for the correction), and a frame's dt is clamped to 0.05 on the client, the cap the server puts on an input's dt (2026-10-18: before this, every arrow cast while moving snapped the body back about a tile, bolts hopped 1.3 tiles ten times a second, and a slow frame over-predicted). `reconcile` fills `window.__dbg` with one record per correction when the headless rig sets it; `MOBS=0` starts the server without the arena's monsters, and `server/lag-proxy.mjs` serves the game through a one-way delay, both for measuring this on the desk. The round-end board shows the top five and your own line (fifty in the ring would scroll off a phone).

**The presenter's view** (`?watch=1`, 2026-10-18, for the webinar's finale shared over Discord at 720p): a body like any other, under a token kept in the tab's sessionStorage (so the same desktop can still play on its own token), named Watcher, standing at the spawn and never moved (`collectInput` returns nothing and no input is sent). The HUD is gone (`body.watch` hides it in CSS), the toasts and the round-end board stay, and the sound listens from the ring. Top right, `#watch`: the round in a line (fight in N, standing of N, who stands alone, N in the ring) and the session's leaderboard, the server's tally for watchers only (`tally` in server.js, from the same events the action log sees: wins = rounds won, outs = players knocked out of a round, hits on players; monsters count for nothing; memory only, a restart empties it; ten rows in each snapshot to clients whose `auth` carried `watch: 1`). ## Items, the chessboard, the notice boards

Items are world objects with server-owned state: `{id, kind, x, y, z, rot, state}` in `w.items` (`addItem` in `sim.js`). One chessboard sits on the house table; two notice boards stand by the spawn signpost and on the house wall beside the door. Using a notice board opens a list of its notes, newest first, with author and age, and a box to pin your own (200 characters, one every 5 s per player; the board keeps the newest 40). Notes persist with the rest of the item state and are in the action log. Clicking an item within 2.5 tiles sends `use`; the server replies `open` and the client shows the overlay (`chess.js`). State changes go out to everyone as `item` messages and persist in the `kv` table.

Chess is on the honor system: no rules. Two seats; `use` takes the first free one, others watch. A seated player may move any piece to any square (`applyChessMove`); whatever was on the target square goes into the mover's tray. Turns are a courtesy for playing across days: `turn` says who is to move, the overlay shows it and lists what moved since the turn changed hands (`turnMoves`, highlighted on the board; before anyone moves, the previous turn's moves are shown instead). Either seated player presses `Done: Black's turn` to pass (`chessPassTurn`), which files the turn's start position and moves in `history` (newest last, 40 kept). `Take back` (`chessTakeBack`) first undoes the current turn's moves, then steps back one filed turn at a time, that turn's player to move again; what it removed goes on a `redo` stack and `Redo` (`chessRedo`) puts it back, newest first, until a new move or a passed turn clears the stack. Boards saved before turns existed are upgraded on load (`chessUpgrade`): position kept, the side to move guessed from the last move and the seats. Reset needs both seated players to press it within 20 s of each other, or is immediate when alone. Seats free up on Stand, on disconnect, or when the holder walks more than 3.5 tiles away. Moves and resets are in the action log. Offline the local sim plays the server's part. Backpacks and placing the board elsewhere come later; the item shape allows it.

## Persistence

- SQLite through Node's built-in `node:sqlite` (no native dependency), one file per world seed (`server/world-<seed>.sqlite`), WAL mode. Memory is the game; the database exists so the world survives a restart.
- Terrain is stored per 32x32-tile chunk as one binary blob (`encodeChunk` / `decodeChunk` in `sim.js`): a version byte, the chunk coordinates, then the 33x33 vertices' player-made state (delta, loose, faced). Base terrain is never stored; it comes from the seed. Edge vertices belong to both neighbouring chunks and are written in both. 6.5 KB per chunk.
- `sculpt` and the slope relaxation mark the chunks they touch dirty (`markDirtyVertex`). Every `FLUSH_EVERY` seconds (default 5) the server writes the dirty chunks in one transaction and clears the flags, so a crash loses at most that interval. Shutdown (SIGINT/SIGTERM) flushes first.
- Small state goes in a `kv` table as JSON: the town's ward strength, facing and angle of repose; the animals (kind, position, heading, home). On start the generated herd is replaced by the saved one.
- An append-only `actions` table records joins, leaves, sculpt strokes (one row per held brush, not per frame), guard arrivals and resets, with who, where and when. It is the raw material for disputes and bounties later.
- Players are not persisted yet: there are no accounts, so each connection is a new body at the spawn.

## The ten requirements and where they live

| # | Requirement | Where |
|---|-------------|-------|
| 1 | Low-res render target, integer nearest-neighbour upscale | `main.js` `resize()` sizes the targets to `floor(screen / scale)`; the post pass samples them with `NearestFilter` onto a canvas exactly `scale` times larger. |
| 2 | Camera snapped to the pixel grid | `updateCamera()` rounds the scroll offset to whole pixels in sheared view space and shifts the ortho frustum instead of moving the camera. Objects can also snap individually (`uSnap` in `objVert`). |
| 3 | Zoom by render-target size, fixed pixel size, ~3 steps | "Pixel scale" changes the integer upscale factor; the target is re-sized to match. Keys `-`/`=` and the wheel step it. A separate "Tile width" slider sets world density (UO = 44 px per diamond). |
| 4 | Palette ramps per material | `RAMPS` in `main.js`: 17 materials x 6 colours, baked into a `DataTexture`. The fragment shader picks a ramp index from light intensity (`ramp()` in `objFrag`). |
| 5 | Stepped shading | Intensity is floored to one of 6 steps; the "Palette ramps" checkbox shows the smooth RGB version for comparison. |
| 6 | Palette quantization + ordered dither | 4x4 Bayer (`bayer4`) nudges the intensity before quantization, strength on the "Ordered dither" slider. Terrain gets a per-cell speckle as a cheap texture. |
| 7 | Depth/normal edge pass | `postFrag`: a pixel is darkened when a neighbour is farther in depth (silhouettes) or its normal differs beyond a threshold (creases). |
| 8 | Fixed sun; day/night via palette | `uSunDir` is constant. The "Night" slider scales intensity (drops ramp indices) and tints in the post pass. |
| 9 | UO 45-degree diamond grid, 44x44 | "UO oblique": a top-down orthographic camera with a vertical shear (`shearM`), giving 1:1 diamonds and visible walls. "True ortho" at 30 degrees gives 2:1 diamonds for comparison. |
| 10 | Animation quantized to 8-12 fps | `applyPose()` is sampled on a coarse clock (`animFps`); poses hold between samples. Positions stay continuous. Turning uses a constant angular speed, no easing. |

## Also in the prototype

- **Terraforming**: Sculpt mode (Tab), tools 1-4 (raise, lower, stone facing, clear facing). Heights are `base + delta`. Material comes from height and slope per fragment, so dug ground turns to dirt, pits below sea level fill with water and grow a sand rim, and nothing needs transition tiles. Nothing ever reverts on its own.
- **Angle of repose** (`relax()` / `slumpPair()` in `main.js`): disturbed earth steeper than the stable slope sheds height to its lower neighbour until stable. Undisturbed ground joins in only when it borders something disturbed (an undercut bank slumps into the pit). Stone facing pins vertices and blocks flow across them, so a faced slope holds steeper than the angle. The angle is a slider.
- **Town ward field** (`wardAt()`, `ward()` in `objFrag`): one town at the origin emits a lobe-shaped field, short behind and long in its facing direction. Land is warded above a threshold; a dotted stone line and sixteen wardstones mark it. Sculpting inside summons a guard: instantly in the core, after a delay that grows toward the fringe, never below the threshold. The strength slider stands in for presence and economy until there is a server.
- **Occluder cut-away**: walls and trees nearer the camera than the player, inside a screen-space disc, are discarded with a dithered rim (`uCutout` in `objFrag`).
- **360-degree movement**: WASD is screen-relative; animals wander with continuous headings. UO steering: hold the right mouse button and the character moves toward the cursor, running when the cursor is far (more than about 2.6 tiles on screen). Shift runs with WASD.
- **Jump**: Space, about one tile high (slider), simple gravity, falls off ledges. `maxJumps` on the player is the hook for a double jump later. Air speed is capped at walking speed so running jumps don't go farther. Every creature has a stippled blob shadow, because in this projection a jump is otherwise indistinguishable from walking north.
- **Collision** (`canEnter()` / `moveEntity()` in `sim.js`): one rule for everything that blocks. Rectangles (walls, fences, floors, crate and table tops) live on a half-tile grid as a surface height (things you stand on) and a barrier height (never stood on), grown by the body radius at stamp time. Round things (trees, rocks, posts, obelisks) are exact circles, and the arena's low walls straight segments with round ends (`barrierSegment`; until 2026-10-18 they were rows of five overlapping circles, a comb whose scallops trapped a sliding body), in a per-tile spatial hash: each circle is listed in every tile bucket within its radius plus one tile, so a query reads the one bucket under the point and tests a handful of circles against the body's radius (0.3 for people, 0.35 for deer, 0.1 for bolts). A 5-pixel post blocks a 5-pixel post; a body squeezes through any gap wider than itself. Wardstones and walls of stone are dynamic circles in a short separate list. A player pushing for half a second without progress is wedged and stands still; nobody is teleported (the old nearest-free-spot move, after a second, went straight through thin walls: the search started one tile ahead). A body a hair inside a barrier (the wire rounds positions to a millimetre) may only step out, never further in, and only the authority walks an embedded body out, once the wedge detector has called it stuck; the slide keeps a degree of margin off the surface for the same reason, and positions live on a millimetre grid (`settle`), the snapshot's precision, so client and server decide a slide from identical numbers (a client's replay once walked straight through a stone row and back, 2026-10-18). You may enter a cell when your feet are above its barrier and the surface is at most 0.4 above you; in the air your feet are wherever the jump put them, so a fence (0.8) passes under you and a wall (2.6) does not. Slopes steeper than 45° block like walls, and since loose earth slumps to 38°, only stone-faced banks stop anyone. When the direct step is blocked, the body slides along a wall if most of its motion is parallel to it, otherwise it finds, on each side of the way it wants to go, the smallest turn that is open (probes at 15 degree steps up to 90, then four bisections, so the step ends hugging whatever blocks: a flat wall, a post, a boulder, a row of stones, a steep bank, at any angle), takes the smaller turn, the remembered side when the two are within 6 degrees, the previous frame's side while it is still open, never more than 90 degrees, and moves along it at the push scaled by the turn's cosine, never below `SLIDE_MIN` (0.5). The slide state (`slide`, `avoidSide`, `stalled`) rides in the player's snapshot entry so the predicting client agrees with the authority. History, all 2026-10-18: rotated probes of 40/80/120 degrees shook eight times a second against a wall (the 120 step backed off, the next direct step went back in); 30/60/90 slid against the lean; axis slides plus per-circle tangents left the body stuck from one side of the arena's slanted rows of stones and shaking from the other, client and server disagreeing about which (Bobby's phone trace). Props register footprints where they are created; wardstones are dynamic round obstacles that move with the ward slider. A tap on a thing (a chessboard, a notice board, the arena's stone) is judged on the screen first (`itemAtScreen`, like `markAt` for bodies: within 40 px on touch of the thing's middle, its foot plus `ITEM_LIFT`), then on the ground point under the tap (`itemAt`, 0.8 tiles): the ground ray falls through a raised thing to the ground behind it, about its height away in the oblique view, so taps on the board or the stone mostly did nothing (2026-10-19, Bobby: "I have to tap multiple times"). The trace (`?trace=1`) carries the last taps (`taps`: what each hit, and for a walk the nearest thing and how far off). A chess game under way (a move since the last reset, `chessHeld`) keeps its players: walking off leaves the chair theirs (`chessLeave` refuses to stand them; the server's `tickItems` calls it), so nobody else can sit, move or vote until the two reset; a board nobody has moved on frees its chairs as before. Three more boards stand on tables in the chess garden east of the house path (2026-10-19, for the webinar: students play there, the house table keeps its game); `MYSTICA.mod.boards()` lists them with their chairs, `MYSTICA.mod.chessFree(item)` opens a board's chairs again (the admin's backstop, the position untouched). Mouse steering uses pointer capture, so holding the right button keeps working when the cursor leaves the window. **Three speeds on the stick** (2026-10-19, Bobby): a creep at `CREEP_MUL` (0.3) of a walk within a hair of the centre (`STICK_CREEP`, 45% deflection, above the 15% dead zone; 30% on the first day was too narrow a hair to land in), a walk, a run past 80%. The creep is deliberate (`stickBand` in main.js): on the way out of the centre it is granted only after the thumb has lingered in the band `STICK_CREEP_MS` (150), so a flick passes straight through to a walk or a run and nothing moves meanwhile; on the way back in from a walk or a run it is granted at once. The input carries `creep`, the sim's `applyPlayerInput` sets `e.creeping` (never while running), the snapshot carries `cr` for the other clients' footstep cadence, and the knob dims while creeping. Keyboard and mouse steering have no creep. The page refuses the context menu everywhere but in a text field (document-level `contextmenu`): on a phone a thumb resting on the stick is a long press, and the menu it opened came with a buzz.
- **Water**: depth is negative terrain height. Wading to 0.4 deep is full speed, speed falls to a third by 1.2, and deeper water blocks unless the entity can swim (panel checkbox for the player). No jumping from water.
- **Rocks**: every rock has a real top (`generateProps`). Small ones are platforms you step onto; big ones also carry a barrier at their top, so they block on foot and a jump lands on them.
- **Animals never stay stuck**: a blocked animal picks a new direction at most twice a second; one that walks for two seconds without getting half a tile anywhere turns right round, and after a second such window it is moved to the nearest free spot (`freeSpotNear`).
- **Animal abilities**: deer hop fences (jump when blocked by something under 0.95), sheep can't, nobody swims yet. Mobs will get more (fly, swim, climb).
- **Background tab**: browsers pause the frame loop in hidden tabs; the sim keeps ticking at 10 Hz without drawing. `MYSTICA.sim(seconds)` steps the simulation synchronously for tests.

## Open questions to settle by looking

- Oblique vs true ortho. Oblique matches UO's geometry exactly; judge whether 3D models look right under it.
- Vertical scale `k` in oblique mode. 1.0 makes a 2.6-unit wall about 80 px and a 1.6-unit character about 50 px at 44-px tiles, close to UO proportions.
- Whether per-object pixel snapping helps or hurts for rotating 3D characters.
- Edge thresholds (`uDepthThr`, `uNormThr`) once real models replace the cubes.
